Funciones de ventana

Función de ventana

Son funciones SQL que realizan cálculos sobre el conjunto de filas relacionadas con la fila actual (ventana).

Por ejemplo, calcular una suma acumulada:

Fecha Ventas Suma Acumulada
2023-10-01 4,241 4,241
2023-10-02 2,389 6,630
2023-10-03 1,580 8,210
2023-10-04 3,395 11,605
2023-10-05 1,265 12,870

Cómo se desliza la ventana

Calculando la fila actual

La ventana para la suma acumulada del 2023-10-04 incluye la fila actual y todas las filas anteriores.

Cálculo: 4,241 + 2,389 + 1,580 + 3,395 = 11,605

Avanzando a la siguiente

Cuando pasamos a la fila siguiente, la ventana también se desplaza. Ahora incluirá todas las filas anteriores y la fila actual.

Nuevo cálculo: 11,605 + 1,265 = 12,870

Sintaxis

SELECT column_1,
       column_2,
       <window_function> OVER(PARTITION BY … ORDER BY … <window_frame>) AS column_alias
FROM table;

La cláusula OVER() es el corazón de cualquier función de ventana.

Componentes de OVER()

  • <window_function>: la operación matemática o lógica que vas a realizar.
  • OVER (...): convierte tu función en una “función de ventana”.
  • PARTITION BY ... (opcional): divide los datos en subgrupos o “particiones” independientes.
  • ORDER BY ... (opcional): define en qué orden se evaluarán las filas dentro de cada partición.
  • <window_frame> (opcional): define los límites exactos de tu ventana relativos a la fila evaluada.
  • AS column_alias: el nombre de la nueva columna calculada.

Funciones de Ventana: Agregación

  • COUNT() — cuenta el número de filas dentro de una ventana.
  • SUM() — totaliza valores dentro de una ventana.
  • AVG() — calcula la media de los valores dentro de una ventana.
  • MIN() — encuentra el valor más pequeño dentro de una ventana.
  • MAX() — encuentra el valor más grande dentro de una ventana.

Funciones de Ventana: Clasificación

  • ROW_NUMBER() — clasifica valores secuencialmente, con diferentes rangos para los valores empatados.
  • RANK() — usa el mismo rango para empates; omite el siguiente rango después de un empate (1, 2, 2, 4).
  • DENSE_RANK() — usa el mismo rango para empates; no omite el rango siguiente (1, 2, 2, 3, 4).

Funciones de Ventana: Analíticas

  • LEAD() — obtiene datos a partir de un desplazamiento definido después de la fila actual.
  • LAG() — obtiene datos de un desplazamiento definido antes de la fila actual.

Ejemplo

Tenemos la tabla empleados. Queremos saber quién es el mejor pagado de cada departamento, asignando una posición (ranking) según su salario.

id nombre departamento salario
1 Sofía TI 9000
2 Carlos TI 8000
3 Marta TI 8000
4 Ana Ventas 5000
5 Luis Ventas 3000

La Solución: Query con Función de Ventana

Usaremos RANK() combinada con la cláusula OVER():

SELECT 
    nombre, 
    departamento, 
    salario, 
    RANK() OVER(
        PARTITION BY departamento 
        ORDER BY salario DESC
    ) AS ranking_depto
FROM empleados;

PARTITION BY departamento crea ventanas separadas para ‘TI’ y ‘Ventas’. ORDER BY salario DESC ordena los salarios de mayor a menor dentro de cada ventana.

El Resultado

nombre depto salario ranking
Sofía TI 9000 1
Carlos TI 8000 2
Marta TI 8000 2
Ana Ventas 5000 1
Luis Ventas 3000 2

A diferencia de GROUP BY, la función de ventana devuelve todas las filas originales, con una nueva columna de cálculo dinámico.

💡 Carlos y Marta empatan en 8000 y RANK() les asigna a ambos el puesto 2.

CTEs

CTE: Expresiones de Tabla Comunes

Permiten definir una subconsulta con nombre, reutilizable dentro de la consulta principal.

WITH cte_name AS (
   SELECT
     column1,
     column2, …
   FROM table …
)
SELECT …
FROM cte_name, …;

Ejemplo: salario por encima del promedio

Queremos saber qué personas ganan por encima del promedio de su departamento.

id nombre departamento salario
1 Ana Ventas 5000
2 Luis Ventas 3000
3 Carlos TI 8000
4 Marta TI 7000
5 Sofía TI 9000

(El promedio en Ventas es 4000 y en TI es 8000).

La Solución: Query con CTE

WITH PromedioDepto AS (
    -- 1. La CTE calcula el salario promedio por departamento
    SELECT 
        departamento, 
        AVG(salario) AS salario_promedio
    FROM empleados
    GROUP BY departamento
)
-- 2. La consulta principal usa la CTE como si fuera una tabla real
SELECT 
    e.nombre, e.departamento, e.salario, p.salario_promedio
FROM empleados e
JOIN PromedioDepto p ON e.departamento = p.departamento
WHERE e.salario > p.salario_promedio;

El Resultado

nombre departamento salario promedio
Ana Ventas 5000 4000
Sofía TI 9000 8000


💡 ¿Por qué usar una CTE? Podríamos resolverlo con subconsultas anidadas, pero la CTE hace que el código sea más limpio, lógico y fácil de leer paso a paso.

CTEs Recursivas

Una CTE recursiva hace referencia a sí misma dentro del SELECT, creando un bucle.

Se utilizan para recorrer estructuras de datos jerárquicas, como organigramas o redes.

Sintaxis

Requiere la palabra RECURSIVE y se compone de: ancla, UNION y miembro recursivo.

WITH RECURSIVE cte_name AS (
    -- 1. Consulta Ancla (caso base)
    SELECT column_1, column_2
    FROM table_name
    WHERE condition

    UNION ALL

    -- 2. Consulta Recursiva (referencia a cte_name)
    SELECT t.column_1, t.column_2
    FROM table_name t
    JOIN cte_name c ON t.parent_column = c.column_1
)
SELECT * FROM cte_name;

Ejemplo: Jerarquía de una Empresa

Cada persona tiene un jefe (jefe_id), excepto la CEO, con valor NULL.

id nombre jefe_id puesto
1 Elena NULL CEO
2 Roberto 1 Director TI
3 Laura 2 Desarrolladora
4 Tomás 3 Becario

Objetivo: ver la jerarquía completa por nivel (Nivel 1 = CEO, Nivel 2 = Director, etc.).

La Solución: Query Recursiva

WITH RECURSIVE Jerarquia AS (
    -- 1. Ancla: empezamos por la CEO (nivel más alto)
    SELECT id, nombre, jefe_id, 1 AS nivel
    FROM empleados
    WHERE jefe_id IS NULL
    
    UNION ALL
    
    -- 2. Recursividad: buscamos a quienes reportan al nivel anterior
    SELECT e.id, e.nombre, e.jefe_id, j.nivel + 1
    FROM empleados e
    JOIN Jerarquia j ON e.jefe_id = j.id
)
SELECT nombre, nivel FROM Jerarquia;

El Resultado

nombre nivel
Elena 1
Roberto 2
Laura 3
Tomás 4

El motor ejecutó el caso base (Elena). En el primer bucle encontró a Roberto (nivel 2), luego a Laura (nivel 3), y así hasta que nadie reportó a Tomás.

Optimización de consultas

El Proceso de Optimización de Consultas

Optimizar código SQL no se trata de adivinar, sino de seguir un método científico.

Este es el flujo de trabajo estándar en la industria de datos para transformar una consulta lenta en una eficiente.

1. Identificar y Entender

Antes de tocar una sola línea de código, debes entender el contexto.

  • Entender el objetivo: ¿qué intentaba lograr el autor original? A veces es más rápido replantear la lógica desde cero que emparchar una consulta mal diseñada.
  • Identificar el cuello de botella: ¿el problema es el tiempo de ejecución, el alto consumo de CPU, o que bloquea otras transacciones?
  • Revisar la volumetría: ¿estás consultando una tabla de 1,000 registros o de 500 millones? Las estrategias cambian según el tamaño de los datos.

2. Analizar el Plan de Ejecución

Nunca optimices a ciegas.

EXPLAIN o EXPLAIN ANALYZE muestra el plan de ejecución que el motor va a usar para resolver una consulta: qué índices utiliza, en qué orden accede a las tablas y qué método de join aplica.

Sirve para detectar table scans innecesarios, elegir mejores índices y reescribir consultas costosas antes de llevarlas a producción.

EXPLAIN
SELECT nombre, salario
FROM empleados
WHERE departamento = 'TI';

Red Flags en el Plan de Ejecución

  • Full Table Scans — escaneos completos de tabla.
  • Nested Loops muy grandes — bucles anidados costosos.
  • Uso de memoria temporal en disco en lugar de en RAM.

3. Revisar Índices y Estructura

El código SQL puede ser perfecto, pero sin la estructura física adecuada, seguirá siendo lento.

  • Revisa las llaves: ¿las columnas usadas en JOIN, WHERE y ORDER BY están indexadas?
  • Tipos de datos: ¿estás comparando un texto (VARCHAR) con un número (INT)? Las conversiones implícitas destruyen el rendimiento.
  • Equilibrio: los índices aceleran la lectura (SELECT), pero ralentizan la escritura (INSERT/UPDATE). No crees índices “por si acaso”.

4. Refactorizar el Código

  • Sustituye subconsultas complejas por CTEs para mejorar la legibilidad y ejecución.
  • Mueve los filtros WHERE lo más “arriba” posible para reducir el volumen de datos antes de los JOINs.
  • Asegúrate de que tus filtros sean sargables (no apliques funciones matemáticas o de texto directamente sobre la columna en la cláusula WHERE).
  • Elimina SELECT * y DISTINCT innecesarios.

5. Pruebas y Benchmarking

El último paso es validar con datos duros que tu nueva versión es mejor.

  • Mide el antes y el después: ejecuta ambas consultas y compara sus tiempos de respuesta y su costo en el plan de ejecución.
  • Limpia la caché: vacía la caché de la base de datos antes de probar. Ejecutar la misma consulta dos veces da falsos positivos, porque la segunda siempre es más rápida al tener los datos en memoria.
  • Implementa: si los resultados son sólidos, la consulta está lista para producción.

Ejercicio 1: Combine Two Tables

Nivel: Fácil

Enfoque: uso correcto de combinaciones externas (Outer Joins).

Descripción: dadas las tablas Person y Address, el script debe reportar el primer nombre, apellido, ciudad y estado de cada persona. Si la dirección de un ID de persona no está presente en Address, se reporta como null.

Link: leetcode.com/problems/combine-two-tables

Ejercicio 2: Second Highest Salary

Nivel: Medio

Enfoque: subconsultas, manejo de valores vacíos y cláusulas de filtrado condicional.

Descripción: encontrar el segundo salario más alto de la tabla Employee. Si no existe, la consulta debe retornar null en una sola columna.

Link: leetcode.com/problems/second-highest-salary

Ejercicio 3: Consecutive Numbers

Nivel: Medio

Enfoque: funciones de ventana analíticas (LEAD/LAG) o combinaciones múltiples sobre la misma tabla (Self-JOINs).

Descripción: encontrar todos los números que aparecen al menos tres veces consecutivas de manera ininterrumpida dentro de la tabla Logs.

Link: leetcode.com/problems/consecutive-numbers

Ejercicio 4: Department Top Three Salaries

Nivel: Difícil

Enfoque: expresiones de tabla comunes (CTEs) y funciones de ventana avanzadas de clasificación.

Descripción: una empresa considera “alto asalariado” a un empleado si su salario está entre los tres primeros salarios únicos de su departamento. Escriba una consulta para encontrar a esos empleados en cada departamento.

Link: leetcode.com/problems/department-top-three-salaries
